# support-rag-bot

Telegram-бот первой линии поддержки для вымышленной SaaS-платформы «ТренингХаб» (обучение сотрудников по охране труда). Отвечает на вопросы клиентов по базе знаний (RAG), передаёт сложные случаи живому оператору, ловит выдумки модели кодом и ведёт журнал диалогов для разбора качества.

> Учебный проект. Продукт, компания и база знаний вымышлены.

![CI](https://github.com/IlyaSalih/support-rag-bot/actions/workflows/ci.yml/badge.svg)

## Что умеет

- **Отвечает по базе знаний** — 21 статья в Markdown: вход, сотрудники, курсы, тесты, документы, отправка в госреестр, тарифы.
- **Передаёт оператору**, когда ответа в базе нет, когда по статье случай требует человека («статус висит больше 5 рабочих дней») или клиент раздражён без конкретики. Эскалации приходят в отдельный чат операторов.
- **Отказывает** в том, чего бот сделать не может («сбросьте мне попытки» — это делает администратор компании), и на вопросы не по теме.
- **Защищается от выдумок кодом** — ответ с числами, которых нет в статьях, или ответ «про другое» клиенту не отправляется.
- **Бережёт персональные данные** — предупреждает клиента, приславшего СНИЛС или телефон, и маскирует их в журнале и в пересылке операторам.
- **Собирает обратную связь** — кнопки «👍 Помогло / 👎 Не помогло»; «не помогло» уходит оператору вместе с ответом бота.

## Архитектура

```
Клиент в Telegram
      │
      ▼
 app/bot.py ── предупреждение о ПДн, кнопки оценки, журнал logs/dialogs.jsonl
      │
      ▼
 app/answer.py
      │
      ├─► app/retriever.py — гибридный поиск по 171 фрагменту базы знаний
      │       ├─ по смыслу: эмбеддинги paraphrase-multilingual-mpnet-base-v2
      │       │             (локально, fastembed/ONNX, без GPU и без платного API)
      │       ├─ по словам: BM25 со стеммингом для русского (app/lexical.py)
      │       └─ объединение рейтингов: Reciprocal Rank Fusion
      │
      ├─► GigaChat-2 — ответ строго по 3 найденным статьям,
      │               метка решения [ANSWER] / [ESCALATE] / [DECLINE]
      │
      └─► app/grounding.py — проверка ответа кодом:
              числа в ответе должны быть в статьях,
              слова ответа должны совпадать со статьями
                    │
                    ▼
        ответ клиенту  или  эскалация в чат операторов
```

**Стек:** Python 3.12, aiogram 3, GigaChat API, fastembed, ChromaDB, Docker, GitHub Actions.

**Почему так:**
- Эмбеддинги GigaChat платные (402 на бесплатном тарифе) — поэтому эмбеддинги считаются локально, а API используется только для генерации ответа.
- Статьи передаются модели **целиком**, а не фрагментами: в первых прогонах поиск находил блок «Когда писать в поддержку» раньше самого решения, и модель отвечала «напишите в поддержку» вместо инструкции.
- В базе знаний у каждой статьи есть поле `questions` — типичные формулировки клиентов. Вопрос клиента по смыслу ближе к другому вопросу, чем к тексту инструкции.

## Как измерялось качество

Два набора вопросов в `eval/`:
- **`questions.yaml`** — 40 вопросов, на которых система настраивалась;
- **`holdout.yaml`** — 18 отложенных вопросов, по которым настройки не подкручивались.

Для каждого вопроса проверяется решение бота (ответить / передать / отказать), обязательные и запрещённые фрагменты в ответе и то, нашёл ли поиск нужную статью. Скрипт: `python -m eval.run_eval`. Отдельно `python -m eval.rank_check` показывает, на каком месте поиск ставит нужную статью, — без обращения к API.

### Как менялся результат

| Шаг | Основной набор | Поиск |
|---|---|---|
| Базовый RAG: MiniLM, поиск только по смыслу | 65% | 76% |
| Типичные вопросы клиентов в статьях, правила эскалации | 80% | 73% |
| Модель эмбеддингов mpnet, пересчитанный порог | 82% | 84% |
| Гибридный поиск (смысл + BM25), 3 статьи в контекст | 92% | 100% |
| Защита от выдумок кодом | 90% | 100% |

На **отложенном наборе**: поиск 100%, автопроверка 61%. При ручном разборе провалов большая часть — спорная разметка или проверка, не нашедшая нужное слово в верном по смыслу ответе. **Опасных ответов** (бот уверенно сказал неправду) — 1 из 18.

Между прогонами результат колеблется на 1–2 вопроса: GigaChat отвечает не полностью одинаково даже при низкой температуре.

## Защита от выдумок: что пробовали

Самая опасная ошибка бота поддержки — уверенный неверный ответ. На отложенном наборе GigaChat-2 выдумал цены тарифа («15 000 ₽, 27 000 ₽…» — цен в базе нет) и сообщил, что интеграции с 1С «нет», хотя в базе о ней ни слова.

| Подход | Результат |
|---|---|
| Правило в промпте «не выдумывай» | Модель его не соблюдала |
| Модель прикладывает цитату из статьи, код проверяет цитату | Отказались: выдуманные цены шли вместе с настоящей цитатой — модель цитирует формально |
| Проверка отрицаний («не может» vs «может») | Отказались: ложные срабатывания на 16 честных ответах из 51 |
| **Числа в ответе должны быть в статьях или в вопросе** | Поймала выдуманные цены, ноль ложных срабатываний на 58 реальных ответах |
| **Доля слов ответа, совпадающих со статьями ≥ 0.35** | Поймала выдуманный отказ про 1С (0.14 при минимуме 0.42 у честных ответов) |

Пороги подобраны по реальным ответам модели, сохранённым в отчётах прогонов, а не наугад.

## Разбор живых диалогов

Бот пишет журнал `logs/dialogs.jsonl`: вопрос (с маскировкой ПДн), решение, найденные статьи, срабатывания защиты, ответ, оценку клиента. По первым ~50 живым диалогам найдено и исправлено:

- клиент прислал СНИЛС в чат, бот не предупредил — **добавлено предупреждение кодом**;
- при эскалации модель писала «напишите в поддержку» рядом с «передаю специалисту» — **противоречие убирается кодом**;
- в 7 из 32 ответов модель отправляла клиента «писать нам», хотя он уже в поддержке — **заменено подсказкой про кнопку «Не помогло»**;
- маскировка скрывала адрес рассылки самой платформы — **собственный домен исключён**.

## Известные ограничения

- **Тонкие выдумки словами из статей не ловятся.** Пример: «загрузить свой курс нельзя» — совпадение со статьями как у честных ответов. Для этого нужна проверка второй моделью.
- **Пересчёт единиц принимается за выдумку.** Клиент пишет «раз в 2 года», бот отвечает «24 месяца» — защита отдаёт вопрос оператору. Ошибка безопасная, но лишняя.
- **Оценки 👍/👎 хранятся в памяти** — после перезапуска старые кнопки не работают.
- Бот обрабатывает каждое сообщение отдельно, без истории диалога.

## Что можно улучшить

- Проверка ответа второй, независимой моделью — против тонких выдумок.
- История диалога в контексте: уточняющие вопросы «а как это сделать?».
- Отчёт по журналу: частые вопросы без ответа в базе, доля 👎 по статьям — список того, что дописать в базу знаний.
- Прогон тестового набора в CI по расписанию (нужен секрет GigaChat).

## Запуск

Нужны: Docker с Compose, ключ GigaChat API (developers.sber.ru, бесплатный тариф для физлиц), токен бота от @BotFather.

```bash
git clone https://github.com/IlyaSalih/support-rag-bot.git
cd support-rag-bot
cp .env.example .env        # вписать GIGACHAT_CREDENTIALS и TELEGRAM_BOT_TOKEN
docker compose up -d --build
docker compose logs -f
```

Сертификаты Минцифры для GigaChat уже лежат в `certs/` и ставятся в образ. При первом запуске скачивается модель эмбеддингов (~1 ГБ) в том `data/`.

**Чат операторов (необязательно):** создать группу, добавить в неё бота, написать `/chatid` и вписать полученный id в `.env` как `OPERATORS_CHAT_ID`.

### Разработка без Docker

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python -m app.ingest                       # индекс базы знаний
python -m app.answer "ваш вопрос"          # ответ без Telegram
python -m app.bot                          # бот
pytest                                     # юнит-тесты
python -m eval.run_eval                    # качество на тестовом наборе
python -m eval.run_eval --file holdout.yaml
```

## Структура

```
app/            код бота: поиск, ответ, защита от выдумок, Telegram, журнал
knowledge_base/ 21 статья базы знаний
eval/           тестовые наборы и скрипты оценки качества
tests/          юнит-тесты (без API и моделей — запускаются в CI)
docker/         точка входа контейнера
certs/          корневые сертификаты Минцифры для GigaChat
```

## CI

`.github/workflows/ci.yml` на каждый пуш: юнит-тесты → сборка Docker-образа → публикация в `ghcr.io`. На pull request образ только собирается.
